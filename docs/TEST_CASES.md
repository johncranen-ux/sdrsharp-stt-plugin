# Test Case Catalogue

This document surveys the project's test suite as of 2026-09-17: what each test file covers, what
type of test it is, which business/technical requirement (from `CLAUDE.md`) it verifies, the
testing strategy it uses, and how to run it. It was generated by reading the test files and their
module docstrings directly, not from a design document, so descriptions are grounded in what the
code actually does. Where a test's purpose or requirement mapping wasn't obvious from its content,
that is noted rather than guessed.

The suite spans two languages and two very different execution environments:

- **C# / .NET 9** (`SDRSharp.SttPlugin.Tests`) — pure-logic unit tests for the SDR# plugin's DSP
  and networking code, run with `dotnet test`. (`CLAUDE.md` specifies .NET 8; the shipped test and
  plugin projects both target `net9.0` — a discrepancy from the original requirement worth flagging
  rather than silently resolving.)
- **Python** (`server/tests`) — unit, integration and end-to-end tests for the WSL-side STT proxy,
  its control-panel web app, and a family of offline measurement/benchmark harnesses, run with
  `pytest`.

There is no JavaScript/TypeScript test suite. The control panel's frontend (`server/webapp/static/`)
is plain HTML/CSS/JS with no build step and is exercised only indirectly, through the FastAPI route
tests that serve it.

A large and distinctive part of this project's testing is **empirical measurement**, not
pass/fail assertions: scripts like `bench.py`, `bench_identify.py`, `bench_prompt_ab.py` and the IQ
replay harness score transcription/identification quality against hand-labelled ground truth and
produce numbers (WER, precision/recall) that get written up in project memory rather than checked
by an `assert`. These are covered separately below as **measurement harnesses**; their *own*
correctness (parsing, scoring arithmetic, aggregation) is what the corresponding `test_bench*.py`
files unit-test.

greps for credential-shaped literals and any committed file family known to carry real received
radio traffic (reference transcripts, bench/replay result JSON, few-shot example files).

## 1. SDR# Plugin — C# unit tests (`SDRSharp.SttPlugin.Tests`)

All tests here are **unit tests** against pure logic files that are *linked* (not project-referenced)
from the main plugin project specifically so the test project stays portable — the real plugin
project targets `net9.0-windows`/x86 and pulls in WinForms plus the SDR# SDK, neither of which the
DSP/networking logic depends on. This is also why CI can build and run these tests on
`windows-latest` without ever building the plugin itself.

| File | Covers | Requirement | Strategy | Cases |
|---|---|---|---|---|
| `BiquadFiltersTests.cs` | DC-blocking and high-pass biquad filters | Audio-chain quality ahead of STT (no formal BR, supports "least errors" goal) | Deterministic signal-in/signal-out assertions (constant offset, AC passthrough, dB attenuation measurement, state reset) | 4 |
| `DecimatorTests.cs` | Resampling/decimation (`Decimator.cs`) | Same — feeds the audio pipeline before chunks are sent to Whisper | Synthetic tone/DC signals; anti-aliasing checked via measured dB rejection; edge cases (same-rate, empty input, non-integer ratio) | 6 |
| `NormalizerTests.cs` | Peak normalization before chunks are sent | Same | Peak-scaling assertions, near-silence and empty-input edge cases, output never exceeds full scale | 4 |
| `VoiceActivityDetectorTests.cs` | `VoiceActivityDetector` (onset/offset hysteresis, pre-roll buffering, squelch override, min-speech-length rejection) | **BR: "Plugin should support Voice Activation Detection (VAD), so no empty or Static chunks are sent to the STT Server"** — this file is the direct test of that requirement | State-machine tests using a slow/low sample-rate config for readable frame-count math; each test documents *why* the boundary matters (e.g. squelch click must not open speech, mid-level dip must not close a segment) | 6 |
| `WavBuilderTests.cs` | WAV header construction and resampling for the outbound HTTP payload | BR: plugin → STT server audio delivery | Byte-level header assertions, clipping of out-of-range samples, empty-input and same-rate edge cases | 5 |
| `WhisperClientTests.cs` | URL parsing for the Whisper server endpoint, and JSON response text extraction (`ExtractText`) | BR: "Speech Chunks... need to be sent to a STT server... and the transcribed text sent back" | Theory-driven URL parsing table (valid/invalid schemes, ports, paths); regression cases for a former substring-based JSON parser (escaped quotes, unicode, malformed JSON) explicitly called out in comments | 10 |
| `PluginSettingsTests.cs` | Default value of the Whisper prompt setting | Design decision: the proxy, not the plugin, owns the transcription prompt | Single assertion pinning a default | 1 |

**Not covered here:** actual network I/O to the Whisper server (no integration test issues an HTTP
request — `WhisperClientTests` only tests the pure parsing/formatting helpers), and no test exists
against the live SDR# host process itself (that's inherently untestable in CI; see the manual
verification steps in project memory instead, e.g. `sdrsharp_plugin_load_failures.md`).

**Notable safety mechanism:** `server/tests/conftest.py` carries three `autouse` fixtures born from a
real 2026-08-18 incident where a route test built a `Supervisor` over the *real* log directory
(because a missing config file made every setting fall back to its production default) and killed a
live proxy that was carrying real radio traffic for twenty minutes. The fixtures now make it
structurally impossible for any test to reach the real supervisor, the real 1.5 GB capture
directory (also legally gitignored under NL Telecommunicatiewet 18.13), or the real conversation
archive — each raises `AssertionError` with the incident's own explanation if a test tries. This is
the single most load-bearing piece of test infrastructure in the repo and is worth preserving
verbatim in any future refactor.

Mapping `CLAUDE.md`'s Business Requirements to where they're tested. This is a best-effort mapping
based on file content and docstrings, not a formal traceability matrix — several requirements are
covered only indirectly (e.g. through the DSP chain or through manual/measurement verification
rather than an automated assertion).

|---|---|---|

| STT server local in WSL, GPU is AMD RX7900XTX/ROCm | Not testable in CI by nature (`.github/workflows/ci.yml` explicitly runs with no GPU) | Verified manually per project memory (`server_setup.md`, `gpu_driver_hang_and_watchdog.md`); not part of the automated suite |

## 4. How to run everything

```powershell
# .NET plugin unit tests
dotnet test SDRSharp.SttPlugin.Tests\SDRSharp.SttPlugin.Tests.csproj -c Release

# Python proxy/control-panel/harness tests
python -m pytest server\tests -q
# (individual file headers use `py -m pytest server/tests -v` — same suite, verbose)

# A single Python test file
python -m pytest server\tests\test_whisper_proxy.py -q
```

CI (`.github/workflows/ci.yml`) additionally runs `pyflakes` (undefined-name check only) and a
hygiene job that blocks committing credential-shaped strings or any file family known to carry real
received radio traffic.

## 5. Known caveats worth remembering

- `test_secure_file.py` only runs on Windows (`os.name == "nt"`); CI's Linux runners never execute it.
- `test_control_panel_end_to_end.py` and `test_settings_end_to_end.py` are skipped entirely unless
  `start-all.bat` exists in `server/` — they will silently not run in an environment where that
  file is absent.
- `test_traffic_snapshot.py` is skipped unless `tools/traffic_snapshot.py` exists.
- The `conftest.py` production-isolation guards (§2.2) are safety-critical, not incidental — any
  refactor of `webapp/supervisor.py`, `webapp/clips.py`, or `conversation_archive.py` should keep
  them intact and re-verify they still trip.
- `test_whisper_proxy.py` at 327 test functions is disproportionately large relative to every other
  file; it is currently the de facto specification for most of the proxy's runtime behavior in one
  file.
- No standalone test file for `stt_proxy/corrections.py` (regex-based nautical term correction) was
  found; if it has dedicated tests they were not located as a separate file and may be folded into
  `test_whisper_proxy.py` — worth confirming directly rather than assuming either way.
- `test_proxy_data.py` has no module docstring, so its scope wasn't confidently characterized beyond
  "proxy-side data plumbing for the control panel."
